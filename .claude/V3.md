# V3 — Accounts tracker (traders portfolio). COMPRESSED Aug 12.
# Read V1.md + V2.md first. Live at /accounts_tracker; backend/traders/.

GOAL: simple TABLE dashboard for ~3 wallets (his own, brother, friend) because
Polymarket's portfolio analytics are poor. Wallets shown separately, no charts.
Billed as its own piece; ITEMS 4 (entry/exit alerts) AND 6 (custom tags) are
billable extras the client asked to be priced — the USER sets prices.

## ARCHITECTURE (backend/traders/, one job per file)

  fees.py     flat schedule — FALLBACK ONLY (see FEES)
  dataapi.py  shared-httpx data-api client; fetch_fills = takerOnly double-
              fetch, maker/taker classified AT INGEST (only works inside the
              10k window); fetch_fill_fees = exact cash fees from activity
              usdcSize; fetch_resolution = CLOB /markets/{cid} winner flags;
              fetch_value 3s timeout (flaky + cosmetic)
  store.py    trader_accounts / trader_fills (role+fee stored FOREVER — the
              10k offset cap makes our store the only depth) / trader_tags
              (tag on the ROUND TRIP = (account, asset); all_tags = vocab) /
              trader_resolutions (persisted — closed markets are final;
              without it every restart re-fired a ~200-lookup CLOB storm that
              Cloudflare 403'd and losses silently vanished)
  engine.py   weighted-average matching per (account, asset) — matches the
              avgPrice Polymarket shows; partial exits; EPS 0.01 shares
  service.py  sync throttle 120s + _match_cache 10s WITH in-flight lock
              (summary/open/closed share one pass; sync invalidates);
              _positions 20s, _act_cache 30s, _res_cache + semaphore(8);
              _redeems_as_sells; ghost resolution two-pass; _alive() filter;
              peak_after (our ticks first, CLOB fallback, _sustained_max)
  api.py      /api/traders: add by URL/0x, summary, open, closed, activity,
              tags vocab, tag toggle, sync(force), peak, delete

## MATCHING / P&L RULES (all settled with the user — do not relitigate)

- WIN = round trip netted > $0 AFTER fees. Win rate = wins / closed trips.
- Fees included in net; DISPLAY headline P/L is BEFORE fees (reconciles with
  the profile page, which ignores fees) with "(X after fees)" beneath.
- REDEEM = exit priced by CASH RECEIVED: price = usdcSize/size clamped 0..1.
  NEVER assume $1 — Polymarket sweeps LOSING positions as full-size REDEEMs
  with usdcSize=0 (was size=0 before Aug 11); the $1 assumption made phantom
  100c wins. REDEEM rows carry EMPTY asset — resolve via (conditionId,
  outcome) map from stored BUY fills; size<=0 redeems skipped.
- /positions DROPS resolved-lost holdings ("ride-to-zero losses vanish") —
  residual net-long trips absent from /positions resolve via CLOB winner
  flags: winner -> $1, loser -> $0; unknown stays open (conservative),
  retries 600s, persisted once closed. curPrice==0 rows are dead regardless
  of redeemable, excluded from open side (else double-counted).
- FEES: exact from activity usdcSize (usdc − p*s buys / p*s − usdc sells;
  makers ≈ 0). /activity AGGREGATES partial fills that /trades splits — a
  transaction's leftover cash fee is apportioned across unmatched fills
  weighted by size*p*(1−p) (_assign_fees). update_fees re-stamps stored
  fills every sync (self-healing). Old flat schedule (takers only; sports
  .05, crypto .07, politics .04, geo 0; fee = sh*rate*p*(1−p)) = fallback for
  fills beyond the activity window; rates changed mid-2026 (3%->5% sports) so
  the schedule can NEVER be trusted across time. CLOB maker_base_fee fields
  are junk. Profile P/L (user-pnl-api) is PRE-FEE; reconcile gross vs it
  (~$15 drift = mark timing).
- Peak-after-exit: _sustained_max (pairwise min of consecutive ticks) — a
  dying market's midpoint snaps to ~50c for one final poll (empty ask side);
  lone spikes are artifacts. Phrasing branches on close_reason.

## "COMEBACK SETUP" TRIGGER — spec'd Aug 13, UNBUILT, awaiting go-ahead

Client's ask: tag + alert when home team trails by EXACTLY 1, inning >= 7
(pref >= 8), pref bottom half, a NEW pitcher just entered for the leading
(away) side, and that pitcher is tired (consecutive days / recent WHIP > 1.35
over last 8-15 apps / previous outing >= 25-30 pitches). Red row, flashing,
STAYS until acknowledged. Fire once per occurrence. All thresholds
configurable (min inning, require-bottom, require-consecutive-days, WHIP).
Log every trigger with full context for later review + backtest.
BILLABLE — bill like items 4/6; USER sets the price.

WHAT HE IS ACTUALLY BUYING: latency arbitrage, not analytics. A tiring
reliever protecting a 1-run lead moves true win probability instantly;
Polymarket's price is anchored to the scoreboard and lags. He wants to be on
the home side inside that window. SUCCESS METRIC IS SPEED, NOT ACCURACY — a
correct alert 90s late is worthless. Judge every design choice against that.

ALREADY BUILT (scope is smaller than it reads): live.py polling (3s
linescore, POLL_CONCURRENCY 8), pitcher-change detection -> PITCHER CHANGED
badge, alert/sound/toast stack, row highlights, tags, pen_used_last3,
daily league reliever ERA/WHIP table, backtesting module.
NEW WORK: pitcher-ID tracking (today we watch a COUNT, not who), per-pitcher
gameLog cache, composite trigger eval, LATCHING alert state (today's toasts
expire at 40s), config panel, trigger log.

THREE LANDMINES:
1. He names /feed/live (GUMBO). That is the ONE endpoint we never call —
   634KB, flooded the worker twice (V2 house rule). Same facts come from the
   3KB linescore + field-filtered playByPlay (487KB -> 7.3KB). Honour the
   intent, ignore the literal endpoint, and tell him why.
2. Our current detection is TOO SLOW for this: the relievers-used counter
   only increments ~2min after announcement. Use linescore defense.pitcher,
   which names the new arm much earlier. The known quirk — at an inning break
   defense.pitcher already reports the NEW pitcher while isTopInning has not
   flipped — has been a nuisance everywhere else; HERE it is the asset that
   buys the head start.
3. "Bottom half" vs "pitcher just entered" fight on timing: changes are
   announced DURING the break, before the bottom formally starts. Waiting for
   the half to flip gives away the best of the window. Fire during the break.

DESIGN TRAP: six hard ANDs = a second Clear Favorite — strict, correct and
permanently silent, and in two weeks he asks where the feature went (exactly
the Aug 12 lesson). SCORE the setup and show near-misses, alert at a
threshold, so he sees "Comeback Setup 68 — reliever fresh" on quiet nights.

OPEN QUESTIONS (settle before quoting): alerts only fire while a tab is open
— for a speed trade that is a real limit, server-side push is separate
billable work, flag it BEFORE delivery, not after. Pre-warm reliever
gameLogs pre-game (fetching at trigger time costs seconds exactly when they
are dearest). Log the Polymarket price path alongside the trigger or the log
cannot answer "was there edge". "Exactly 1 run" is narrower than his own
thesis (down 2, tying run on deck is arguably better) — make it a range.
Define "just entered" (announced vs first batter faced) and whether a second
change in the same inning re-fires.

## LIMITATIONS (measured — cite when scoping)

- /trades 10k offset cap (offset=20000 -> 400). Store from day one.
- prices-history: 1-min bars last ~24h, 10-min beyond — spikes invisible;
  OUR ticks (1s/5s) beat it for tracked markets, source labelled in UI.
- Name lookup unreliable (leaderboard only) — parse 0x from pasted URL.
- Deposits/withdrawals/cash = on-chain only (not in any Polymarket API; the
  404 list: /balance /deposits /withdrawals /networth /portfolio /pnl
  /stats). Cash IS public on Polygon if ever wanted.
- polymarketanalytics.com: their API is one authed endpoint with 8 fields,
  no positions/trades/win-rate — paying removes zero work. Their site runs
  its own indexed store (429k trades > 10k cap). Don't reconcile against
  them; the client's profile is ground truth (minus fees).
- MERGE/SPLIT netting, lowest-after-entry, CSV export: deliberately unbuilt.
- Client still owes the three real profile URLs.
