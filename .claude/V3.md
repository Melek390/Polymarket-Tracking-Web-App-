# V3 — Trader portfolio dashboard (spec + API feasibility)

Client brief received Aug 1, 2026. Read V1.md and V2.md first — V3 reuses a lot
of what is already built.

GOAL (client's words): a SIMPLE dashboard to track a few traders' trades —
his own account, his brother's and a friend's — because Polymarket's own
portfolio analytics are poor. He explicitly does NOT want the density of
polymarketanalytics.com/traders/<wallet>. Clean, fast, TABLE-BASED.
NO CHARTS IN V1.

## Verdict: buildable on the FREE official API

Every number the client asked for is reachable without paying anyone. Two
metrics come with a resolution caveat (see "Price-history resolution"), and one
input (profile NAME lookup) has a real gap with a simple workaround.
Nothing in the brief is blocked.

## The build-vs-buy question (client asked)

polymarketanalytics.com pricing, as published:
- FREE — full market analytics, trader leaderboards, up to 7 favourite
  markets/traders/tags/creators.
- PREMIUM — $20/month. 1,000+ favourites and saved views, priority data
  refresh, advanced portfolio tracking.
- ELITE — 1 ETH lifetime, "coming soon".
Their programmatic API ("Falcon", api.polymarketanalytics.com) is SEPARATE and
requires `Authorization: Bearer <token>`, sold B2B — pricing not published.
The site 403s any non-browser request, so it can't be scraped (and shouldn't
be, ToS).

TELL THE CLIENT PLAINLY: he only wants to track 3 accounts. Their FREE tier
allows 7 favourite traders, so the $20 is probably not even needed for what he
described. What he is actually paying us for is (a) a view simple enough to
read at a glance, (b) HIS tags and HIS alert rules, and (c) three metrics they
do not offer — max price after exit, holding time, average-down detection.
That is a fair pitch; do not sell it as "cheaper than $20/mo".

## Requirement -> source map

D = direct API field, C = computed by us, S = our own storage.

### Stat cards
| metric | how |
| --- | --- |
| Portfolio Value | D `/value.value`, or sum `positions[].currentValue` |
| Unrealized P/L | D sum `positions[].cashPnl` |
| Realized P/L | C from matched closed trades (see below) |
| Total P/L | C realized + unrealized |
| Win Rate | C wins / closed trades — NEEDS A DEFINITION, see Open questions |
| Open Positions | D count of `/positions` with size > 0 |
| Closed Trades | C count of matched round trips |
| Holding Time | C first BUY ts -> full-exit ts, from `/trades` |
| Lowest Price After Entry | C min of price history after entry ts |
| Maximum Price Reached (after he sold) | C max of price history after exit ts |
| Average down | C detect >1 BUY at a falling avg price on one asset |

### Tables
- OPEN POSITIONS — D almost entirely: `title`, `outcome` (side), `avgPrice`,
  `curPrice`, `size`, `initialValue`, `currentValue`, `cashPnl`, `percentPnl`.
  Sort by `currentValue` desc (client: "largest position value").
- CLOSED TRADES — C. See "The core computation".
- RECENT ACTIVITY — D `/activity`, render `type` + side + size + price.
  Note it carries MERGE and REDEEM as well as TRADE; don't assume all TRADE.

### Other
- Tags — S. Our table, user-editable. Client's starting list: Bounce, Average
  Down, One Run Behind, Two Runs Behind, Three Runs Behind, First Innings Bet,
  2nd Innings Bet, Bottom Innings, Favorite, Underdog, AFG.
- Category (MLB / Soccer / …) — REUSE `gamma.category_of()` + the
  `events.category` column built Aug 1. Trades carry `eventSlug`
  (`mlb-…`, `wta-…`, `lol-…`, `ufc-…`), so we resolve slug -> Gamma event ->
  tags -> category. Client insisted on real categories, not one "sports" bucket.
- Price alerts — REUSE the whole V2 alert stack (alerts.js, AlertDialog,
  Toasts) + `live_prices.py` for the prices.
- Filters (search market / open-closed / date range) — client-side, same
  pattern as the screener.

## The core computation: closed trades

`/positions` is a HOLDINGS ledger, not a trade log — a position sold out
entirely does not appear (verified: 500 positions returned, none with size < 1).
So realized P/L, win rate, holding time and ROI-per-trade must be
RECONSTRUCTED from `/trades` by matching SELLs against BUYs per `asset`.

This is the real work in V3. Decide and write down: FIFO vs weighted-average
cost. Weighted-average is easier to explain to the client and matches how
Polymarket shows `avgPrice`. Partial exits must be supported — the client
explicitly sells before resolution.
Redemptions matter too: a winning position held to the end settles at 100c via
a REDEEM in `/activity`, not a SELL in `/trades`. Miss that and win rate is
wrong. MERGE also appears.

## Price-history resolution — measured, and it constrains two metrics

`fidelity` is in MINUTES and `interval=max` is capped at 10-minute buckets no
matter what you pass:

| interval | fidelity | points | median gap |
| --- | --- | --- | --- |
| max | 1 or 10 | 81 | 600s |
| 1d | 1 | 796 | 60s |
| 6h | 1 | 361 | 60s |
| 1h | 1 | 61 | 60s |

So: 1-minute resolution for the last ~24h, 10-minute for anything older.
"Lowest price after entry" and "max price after exit" are therefore APPROXIMATE
on older trades — a spike inside a 10-minute bucket is invisible.

OUR ADVANTAGE: for markets the client already TRACKS in this app we store our
own ticks at 5s, and 1s for live MLB (V2: `mlb_poll_interval = 1`). That is far
better than anything the CLOB endpoint returns, and better than what
polymarketanalytics can show. So:
  read our `ticks` table when we have the market, fall back to
  prices-history otherwise, and SAY WHICH in the UI.
This is worth pitching — it is the one place we beat the paid product.

## Adding a trader: name vs URL — a real gap

Client wants to paste a PROFILE NAME or URL.
- A URL or raw address is safe: parse `0x[0-9a-f]{40}` out of anything pasted.
  `/v1/leaderboard?user=<wallet>` resolved an arbitrary wallet fine.
- A NAME is not guaranteed. `/v1/leaderboard?userName=` searches the RANKED
  leaderboard: "swisstony" -> 1 hit, "theo" -> 3 hits, a nonsense name -> 0.
  A low-volume account (exactly what his brother/friend may be) may not be
  indexed at all. Also note many wallets have no display name — the client's
  own example wallet returns the default `0x2c33…-1759935795465`.
DECISION NEEDED: accept wallet/URL as the reliable path, offer name search as
a convenience with "not found — paste the profile URL instead". Do NOT promise
name lookup works for everyone.

## Reuse from V1/V2 — do not rebuild

- Shared httpx client per module (`_http()`). NEVER construct a client per
  call — that was the July 27 event-loop stall.
- Demand-driven server-side cache like `screener/live_prices.py`. Never fan out
  to an upstream API per browser request — that saturated the single worker
  twice.
- Exactly ONE uvicorn worker; collector runs in-process.
- Prices are CENTS 0..100 in the DB; convert at the door. Client wants cents in
  the UI ("23c" not 0.23) — matches what we already do (`fmtCents`).
- Green profit / red loss, `LivePrice` for animated cells, `AnimatedNumber`
  for the stat cards, ET everywhere via `utils.js`.
- The alert system, toasts and the "+ expand row" pattern.

## Open questions for the client

1. WIN RATE DEFINITION. "Winning trades / closed trades" — is a win a
   round trip that netted > $0 after fees, or any SELL above average entry?
   A partial scale-out that banks profit then lets the rest resolve to zero is
   the ambiguous case. Needs his answer before the number means anything.
2. Fees. Polymarket charges per-share fees. Include them in realized P/L, or
   show gross? Affects every P/L number.
3. Does he want his 3 wallets aggregated as one portfolio as well as separately?
4. Tags: per TRADE, per POSITION, or per round trip? He said "tag the trades".
