## ARCHITECTURE / HOUSE RULES (non-negotiable)

- ONE uvicorn worker; collector runs in-process; SQLite WAL `prices.db`.
- ONE shared module-level httpx.AsyncClient per module (`_http()`), NEVER per
  call — per-call clients load the CA bundle synchronously and stalled the
  event loop (July 27; markets 8-12s -> 0.013s after fix).
- NEVER fan out to an upstream API per browser request. Demand-driven
  server-side caches (mlb/live.py, screener/live_prices.py pattern): browser
  polls OUR cache; one upstream fetch per TTL regardless of viewers/windows.
- Prices are CENTS 0..100 in DB and UI; midpoints everywhere (Polymarket's
  `side=buy` price is the BID, not the ask; game pages show the MIDPOINT).
  SETTLED markets: price from `outcomePrices` once closed/resolved — a dead
  book reads bid=null/ask=dust and lies.
- All display times ET (America/Toronto) via utils.js; storage/API/CSV stay UTC.
- localStorage features (alerts, highlights, team tags, hidden rows, notes,
  mutes, account alerts) MUST do BOTH: read-fresh-from-disk on every write AND
  a `storage` event listener — the client runs multiple windows and stale
  in-memory copies erased his data twice.
- position:fixed elements must divide placement by ancestor `zoom` (the A-/A+
  scale) — zoomOf(el) walks getComputedStyle(n).zoom.
- Polling intervals: ONE stable interval with refs, never deps that re-create
  it (re-created intervals discard in-flight fetches -> stuck rows).
- sync_jobs only removes ids starting with "poll-" — it once deleted the named
  background jobs (screener-cache, mlb-live, live-prices) on market close.
- Cache headers (main.py middleware): /api no-store, /assets immutable,
  index.html no-cache. Client must hard-refresh ONCE after any deploy; check
  which bundle a client screenshot implies before chasing "bugs".
- NEVER touch /home/slsks/trading or livetrader.service (client's live bot).

## AUTH (backend/auth/ — LIVE since Aug 13)

Invite-only accounts, cookie sessions, password reset, admin panel. One job
per file like traders/: security.py (stdlib hashlib.scrypt — chosen so no new
wheel is needed and the VM venv never has to be rebuilt), store.py (schema +
all queries; session/invite/reset tokens stored HASHED so a prices.db dump
yields no usable login), sessions.py (HttpOnly + SameSite=Lax cookie — Lax is
why no separate CSRF token is needed — plus per-user/IP login throttling),
deps.py (require_user/require_admin + the PUBLIC-PATH ALLOW-LIST), api.py.

FAIL-CLOSED: a middleware in main.py rejects any /api/ path not on the
allow-list, so an endpoint added later is protected unless someone edits that
list on purpose. Settings: AUTH_ENABLED (must stay true on the VM; false is
the local dev bypass and fakes an admin), AUTH_COOKIE_SECURE (true behind
HTTPS, false for http://localhost or the cookie is silently dropped),
AUTH_SESSION_DAYS / AUTH_INVITE_DAYS / AUTH_RESET_HOURS, AUTH_HEALTH_TOKEN.

FIRST ADMIN = a one-time SETUP LINK, not a password:
  scripts/create_admin.py --link --base-url https://<host>
mints a single-use admin-granting invite when no admin exists; the client
opens it and picks his OWN username and password, so it never passes through
us or shell history. Refused once an active admin exists (not a standing
console backdoor). The direct mode (create_admin.py <name>, --reset-password)
stays as the break-glass path if every admin is ever lost.

HEALTHCHECK WOULD HAVE BROKEN THE DEPLOY: it calls the API with no browser
and so no cookie — all 27 checks would 401 and read as "the deploy broke the
app". It now sends AUTH_HEALTH_TOKEN in X-Health-Token. That token grants NO
user (the admin surface still refuses it); it only passes the blanket
middleware so the smoke tests can read. Empty token = no bypass exists.

BUNDLE/BACKEND DECOUPLING: the auth UI rides in the same JS bundle as
everything else, so a frontend-only deploy would 404 on /api/auth/me and
bounce everyone to a /login the old server cannot serve. fetchMe separates
404 (no auth API on this server -> skip the gate, run as before) from 401
(auth present, signed out -> login page). Verified with one bundle against
both server shapes. This is UI only; the real gate is the middleware.

NO MAIL SERVER: /forgot queues a request the admin sees in the panel and the
admin mints a single-use reset link to hand over. Everything is tokenised, so
adding SMTP later means sending the link instead of returning it.

DEPLOY ORDER MATTERS (get it wrong and the client is locked out of his own
tracker): .env first -> upload, DO NOT restart -> create the admin (the old
service is still running and knows nothing of these tables; SQLite WAL makes
the write safe) -> restart -> healthcheck -> verify login. Kill switch:
AUTH_ENABLED=false + restart reopens the site instantly, no revert needed.

## MLB PIPELINE

- statsapi is free/no-key; flagging = request COUNT. THE FIELDS TRICK:
  `?fields=` shrinks payloads dramatically (linescore 3.2KB; playByPlay full
  487KB -> 7.3KB filtered; boxscore 8.5KB; currentPlay 0.47KB). `fields` can't
  prune the boxscore players map.
- live.py: background job polls the 3KB linescore of LIVE games every 3s
  (POLL_CONCURRENCY 8 — the per-game loop multiplies by slate size, keep it
  concurrent); STATE_TTL 4s; slow cadence SLOW_TTL 20s for pitchers_used +
  inning_extras (walks/durations/home runs — one filtered playByPlay).
  light_state serves cache or ONE light fetch, NEVER feed/live (634KB feed
  fallback twice flooded the worker). Finished games: extras fetched once per
  process. Rows 5-26h old get ONE probe (probedRef) so finals survive reload.
  Six module dicts never evict (deliberate; a few MB/season, restarts clear).
- Status truth: linescore has NO completion flag — Live/Final comes from the
  schedule. Warmup is abstractGameState=Live; preGameLabel shows it and inPlay
  = live && !warmup gates Score/Batting/Outs/Count/Bases.
- offense_defense(ls, ...) from MLB's own offense/defense team ids — at inning
  breaks defense.pitcher already names the NEW pitcher while isTopInning hasn't
  flipped (this broke reliever stats). "-.--" stats -> None (_clean_stat).
- Timing facts (timecode replay — the way to test MLB state changes:
  ?timecode=YYYYMMDD_HHMMSS): relievers counted ~2min after announcement;
  home runs counted from COMPLETED plays only (currentPlay races the batter).
- game_advisory entries in allPlays are admin notes, not plays — filter them.
- MLB posts the announced starter into the boxscore ~3-5h pre-game when
  lineups drop — event badges must ignore non-Live games (risenTeams gates on
  live.status==="Live") or a pre-game row flags PITCHER CHANGED.
- Lineups: starters = players with battingOrder % 100 == 0 (subs get 401);
  prev game's actual SP = teams[side].pitchers[0]; finished-game lineups are
  immutable (cache forever), today's boxscore recheck 300s.
- Backfill: clob interval=max ONE call (paged windows broke on settled
  markets); each outcome lands 1-2s apart so get_ticks merges rows within
  MERGE_SECONDS=2.

## GAMMA PAGINATION CEILING (Aug 23 — entire leagues vanished; NEVER regress)

Gamma /events HARD-REFUSES offset >= ~2100 (HTTP 422) and its DEFAULT sort
is oldest-listed first. Soccer lists ~900 events/day, so on a busy weekend
the newest matchday sat past the ceiling: the screener cache fell to ~34
rows, EPL disappeared entirely WHILE TWO EPL GAMES WERE LIVE (client
caught it, Aug 23). The old code treated 422 as "end of list" — it is NOT;
it is a wall with the newest data on the other side.
FIX (fetch_events_by_tag): page by order=endDate&ascending=true with
end_date_min=now-1d — soonest-ending events (today's games) come FIRST —
and when a window hits the ceiling, advance end_date_min to the last
endDate seen (cursor pagination via the filter, dedup by event id).
Every upcoming event is reachable regardless of listing date; no single
window can outgrow the ceiling. Result: 7,994 events / 1,176 soccer rows
vs 2,100 / ~72 capped. NOTE: start_date_min is the WRONG filter — an
event's startDate is its LISTING date, so early-listed matches would drop.
CHECKER (client asked "some sort of checker"): football/live.py compares
API-FOOTBALL's live big-5 fixtures against screener matches every pass;
a LIVE fixture with no screener row logs a warning and is exposed as
missing_from_screener in /api/football/live. Verified 0 with 3 live.
