## MLB LIVE INCIDENT (July 26) — feed flood + wrong game_pk, FIXED

Client: MLB game live on Polymarket (CLE@TB Bot 4th) but our screener showed
kickoff time, no state, and prices frozen; whole app slow again.
Two bugs (commit d56692d):
1. /api/mlb/game/{pk} non-full fell back to the 634KB /feed/live on a cache
   miss. Frontend BaseballTable polls EVERY "active" row (started within 5h)
   every 3s -> on a full slate (~20-30 games) that's 20-30 x 634KB / 3s ->
   flooded the single worker -> starved state AND price updates. Log was
   wall-to-wall GET /feed/live, zero /linescore (bg poll cache empty).
   FIX: new mlb_live.light_state(pk) -> serves _state cache (STATE_TTL=4s)
   or ONE light /linescore fetch (~3KB), never the feed. Endpoint uses it
   for non-full. mlb_live now keeps _sched{pk:{away,home,status,date}} +
   _state_at. Verified after: 176 /linescore, 0 /feed/live in 60s.
2. _attach_game_pks matched by TEAM PAIR then fell back to kickoff-date-1;
   under load the correct-date lookup failed so it grabbed YESTERDAY's FINAL
   game (CLE@TB row kickoff 2026-07-25T22:10Z got 822952=07-24-Final instead
   of live 822948). Series play consecutive days so pair alone is ambiguous.
   FIX: look across +/-1 day and pick the game whose first-pitch time (new
   schedule "date"=gameDate) is NEAREST the row kickoff. Unambiguous.
Gotchas learned: (a) statsapi schedule?date=YYYY-MM-DD is fine and has the
games (an earlier probe misparsed to 0 — trust totalGames). (b) live CLE@TB
07-25 pk=822948, the 07-26 rematch is 822950, 07-24 was 822952 — adjacent
pks per series, easy to mismatch. (c) BaseballTable DOES poll live-price per
active row (fetchLivePrice) — prices froze only because the worker was
saturated, not a wiring gap.

## CRASH ON SPORT NAVIGATION (July 26) — FIXED

Client: "keeps crashing when I navigate between sports." Root cause: browser
CONNECTION SATURATION, not a render error. BaseballTable polled every game
started within 5h — INCLUDING games finished hours ago (no Final check). Each
Final game's /mlb/game did a statsapi linescore fetch (intermittently hangs
up to the 15s TIMEOUT) and its resolved CLOB tokens returned 404s. ~10-15
such requests every 2s exhausted the browser's ~6-connections-per-host on
hung requests -> navigating (needs a fresh markets fetch) froze.
Fix (commit e3247df):
- BaseballTable active filter: `if (st==="Final") return false` — stop
  polling a game once it's Final (its final score stays cached + shown).
  Only live/upcoming games are polled now.
- backend/mlb/client.py TIMEOUT 15s -> 8s (bounds any slow statsapi call).
Verified: /mlb/game 0.01-1.5s (no hangs), light state includes innings so
ExpandPanel is safe. Note: fetch_buy_prices already swallows 404 per-token.
Client must hard-refresh to get bundle index-iDhtFXfL.js (old bundle keeps
polling Final games until reloaded).

## MLB FEED FLOOD RECURRED (July 26) — FIXED permanently

Client: "website crashed again, prices not moving, MLB state not showing."
markets 2.8s, state stuck "Loading live data…", 26 feed/live (634KB) in 20s.
Cause: /mlb/game NON-full endpoint still had a `return await mlb.live_game()`
fallback after `if state is not None: return state`. When light_state()
returned None (game not in _sched — e.g. schedule fetch throttled/stale),

throttled statsapi -> _sched stays empty -> more misses. Vicious cycle.
Fix (commit 7d45337): non-full now `return await mlb_live.light_state(pk)`
directly (None -> JSON null -> UI shows scheduled time); ONLY full=1 uses
live_game. Cycle can't start. Verified: 0 feed/live, markets 0.23s, active
games return real state (Final scores / live innings).
Context that day: ~02:00 UTC, only 1 live MLB game (07-25 slate finished,
07-26 not started) -> most rows are Final (prices pinned 100/0, correctly
not moving) and now show "Final"; "prices not moving" was largely the games
being over, not a bug. collector had only 9 tracked markets (not a factor).

## STALE BUNDLE / CACHE HEADERS (July 26) — FIXED, important

Client: prices change on Polymarket but not on our UI. Backend was PROVABLY
fresh (our /live-price == CLOB ask, moved 48->50->51 over 18s). Cause: the
SPA was served with Last-Modified but NO Cache-Control, so browsers applied
heuristic caching of index.html and kept running an OLD JS bundle (a normal
refresh reused it) whose render didn't reflect new data. API had no no-store.
Fix (commit bf85aa4): main.py @app.middleware cache_headers:
- /api/* -> Cache-Control: no-store (live data never cached)
- /assets/* -> public, max-age=31536000, immutable (content-hashed JS/CSS)
- text/html -> no-cache (index.html revalidated every load => new deploys
  picked up immediately, no more stale bundles)
Also client.js adds ?_=Date.now() to fetchLivePrice/fetchMlbGame.
IMPORTANT deploy note: clients must HARD-refresh ONCE to drop the old
heuristically-cached index.html; after that no-cache keeps them current.
This is why "hard refresh" was needed after every prior deploy — now fixed
at the source.

## sync_jobs KILLED BACKGROUND JOBS (July 26) — FIXED, important

Client: prices still mismatching (SEA/TEX our 5.1/94.1 vs Polymarket 3.6/96.9;
CLOB truth was 2.0/97.9). Not mid-vs-ask — our value was STALE and frozen.
Root cause: collector sync_jobs() (called at startup AND whenever a market
closes, from poll()) did `for job_id in current - wanted: remove_job`. `wanted`
is ONLY the tracked-outcome "poll-{interval}" jobs, so current-wanted =
{screener-cache, mlb-live, live-prices} -> it DELETED all three named
background jobs the first time any market closed. The live-price poller
stopped => endpoint served the last cached value forever. This ALSO silently
wiped mlb-live/screener-cache (explains earlier "cache empty" flakiness).
Fix (commit dbfadee):
- sync_jobs only removes ids starting with "poll-"; named jobs left alone.
- Defense: live_prices.cached(slug, max_age=8) + endpoint falls back to
  fetch_now if cache >8s old, so a poller stall self-heals.
Verified: our /screener/live-price == CLOB best-ask exactly (2.0/97.9).
NOTE for future: our displayed price is the ASK (buy price, matches
Polymarket's Buy button); Polymarket's game-page % is the MIDPOINT, so a
1-2c residual difference vs that % is the bid-ask spread, NOT a bug.

## LIVE-PRICE POLLER (July 26) — faster prices, server-side cache, LIVE

Client: make live prices faster to catch opportunities. Lesson: dropping
browser poll to 2-3s + endpoint TTL to 2s RE-SATURATED the one worker under
a SINGLE active viewer — ~10 live-price req/s each did a sync DB read +
fresh CLOB fetch on the loop, so /api/screener/markets timed out (8-12s)
again. Load avg was low (~0.7) => request-path contention, not CPU. Never
scale freshness by hitting the CLOB per request.
Fix (commit 9fef05c): demand-driven server-side price poller, same pattern
as mlb_live:
- backend/screener/live_prices.py: _prices{slug:{home,away[,draw]}},
  _wanted{slug:ts}. request(slug) marks viewed; poll() (job every
  settings.live_price_poll_seconds=2) fetches CLOB best-ask for all slugs
  viewed in the last WANT_TTL=90s in ONE batch (clob.fetch_buy_prices),
  caches, and evicts stale. cached(slug)/fetch_now(slug) for the endpoint.
- routes /screener/live-price: request()+cached() (instant) else fetch_now
  one-off. Removed the old per-request TTL+asyncio.Lock cache.
- db.live_screener_tokens() -> (event_slug, token_ids) all rows, feeds poller.
- scheduler adds job "live-prices". Frontend polls baseball 2s / others 3s,
  now instant cache hits.
Result: same live load, markets 8-12s -> ~0.25s. CLOB ~10/s batched by the
poller, viewer-count-independent. tokens are read from screener_cache so a
game must have token_ids (soccer/2-way both stored).

## Price semantics (client asked, investigated in depth)

- Gamma `outcomePrices` == the MIDPOINT, exactly (bid+ask)/2. Verified.
  That is what the screener shows.
- Polymarket's sports "Games" view buttons show the ASK (buy price); their
  market detail "% chance" is midpoint-style.
- On liquid markets spread ~0.1c so they look identical. On illiquid ones
  (e.g. Bolivian league: bid 10c / ask 68c) mid and ask differ by 30+
  points — that was the client's reported "price mismatch". NOT a bug.
- Our tick collector stores CLOB midpoints, so keeping midpoint in the
  screener keeps screener and history consistent. RECOMMENDED (not built):
  add an illiquidity/spread flag on rows with wide bid-ask. Client has not
  chosen yet between: keep mid + flag / switch to ask.
- Also seen: Polymarket postpones fixtures (slug keeps old date,
  gameStartTime updates) — our kickoff follows gameStartTime, correct.
