### THE FIELDS TRICK — how all of this stays cheap

statsapi accepts `?fields=a,b,c` and it is dramatic. MEASURED:
    linescore (what we poll)      3.2 KB
    playByPlay full             487   KB
    feed/live full              704   KB
    playByPlay ?fields=currentPlay…  0.47 KB   <- last pitch / foul
    playByPlay ?fields=allPlays,result,about,halfInning  7.3 KB  <- home runs
    boxscore   ?fields=teams,away,home,pitchers          8.5 KB  <- bullpen count
The 0.47 KB call is SMALLER than the linescore we already fetch. Reach for
`fields` before concluding an endpoint is too heavy to poll.
Caveat: `fields` cannot prune the boxscore `players` map — 8.5 KB is mostly
empty stubs, which is why bullpen/HR counts ride a slower SLOW_TTL=20 cadence.

### MLB TIMING FACTS (measured by timecode replay, don't re-derive)

- A reliever is only COUNTED once he throws his first pitch — the boxscore
  count went 2->3 about TWO MINUTES after the substitution was announced. The
  linescore's defense.pitcher lags the same way. No amount of polling beats it,
  so the PITCHER CHANGED badge is inherently ~1-2 min behind a broadcast.
- Home runs: count COMPLETED plays (allPlays + result.eventType=="home_run",
  halfInning top=away). Watching `currentPlay` races the next batter and would
  miss them.

### PERF: poll() was serial — FIXED before it bit

Senior review caught it. mlb_poll_seconds is 3 (not 5), and poll() looped live
games SEQUENTIALLY. Per game per cycle: linescore 322 ms + last_pitch 168 ms.
On a 15-game slate that is ~7.3 s of serial work inside a 3 s window.
Production logs already showed APScheduler "maximum number of running instances
reached" — but mostly for interval[0:00:01] (the 1 s tick collector, 27 hits in
2 days) and only twice for mlb-live, and they PREDATE this work. So it was a
latent regression, not a live one: last night's slate only had 3-4 games.
FIX: `_poll_game()` gathers a game's calls concurrently, `poll()` gathers games
behind `POLL_CONCURRENCY = 8`.
MEASURED on a simulated 15-game slate: 7.3 s -> 1.91 s cold, 0.51 s warm.
LESSON: anything added inside that per-game loop multiplies by the slate size.

## ===== AUG 2 SESSION — 3 bugs in the new highlight/expand UI =====

All three came in as ONE client complaint ("I can't highlight rows"). They were
three unrelated causes. Lesson: reproduce before theorising, and reproduce in
the CLIENT's conditions, not ours.

### 1. Highlight palette unusable unless the UI text size was 100%

Client couldn't highlight; it worked perfectly for us. Cause: the palette is
`position: fixed` placed from `getBoundingClientRect()`, but App wraps all
content in `<div style={{zoom: scale}}>` for the A-/A+ control.
getBoundingClientRect() reports VISUAL px while a fixed child's top/left get
MULTIPLIED by the ancestor zoom, so the palette drifted further the more the
user had zoomed:
    100% -> +41px (fine)   120% -> +147px   150% -> +308px, OFF-SCREEN
uiScale persists in localStorage, so it was broken on every load for anyone who
had ever touched A+/A-, and correct for anyone who had not.
FIX: `zoomOf(el)` walks ancestors multiplying getComputedStyle(n).zoom; do the
placement math in visual px then DIVIDE by that factor.
VERIFIED at 80/100/120/150/200% — 25 assertions.
=> ANY position:fixed element in this app must divide by the ancestor zoom.
   This is a trap the whole codebase shares.

### 2. "Some rows can't be highlighted no matter how many times I click"

Those rows were the ones CURRENTLY MATCHING AN ALERT. Background was
`alerting ? yellow : highlight`, so the colour saved to localStorage and was
then painted over — clicking again could never help. Which rows are affected
changes as prices move, so it looked arbitrary.
Reproduced with a loose global MLB alert: picking Blue stored
{"mlb-pit-cin-2026-08-01":"blue"} while the row stayed #FEF3C7.
FIX: the highlight WINS the background (deliberate, persistent user mark). The
alert keeps its bell and gains an inset amber stripe down the RIGHT edge of a
highlighted row, so both states read at once. Both tables.

### 3. Expand panel reflowed as data arrived

Client: "sometimes no latest play; sometimes matchup shows then the play feed
appears and pushes it". PlayFeed AND MatchupPanel both `return null` when empty,
so the panel opened without those columns and reflowed as each landed. Plays
only come with the heavy feed (light state is always `plays: []`) and matchup is
a separate fetch on expand, so this happened on EVERY expand of a live game.
FIX: both always render their column; PlayFeed shows "Loading plays…" vs "No
completed plays yet." keyed off the `full` flag (that is what it is for).
MatchupPanel stores `false` on fetch failure so failed != still-loading.
Expanding also fetches full=1 immediately instead of waiting up to POLL_MS.
VERIFIED by intercepting the API to replay the worst case (light instant, full
700ms, matchup 1500ms): matchup column held ONE x position across 3.6s.

### HIGHLIGHTS ARE localStorage ONLY

Asked whether two people highlighting could collide: NO. `screenerHighlights`
is per browser, per device, no server, no API. Same for alerts and presets.
Shared/team highlights would need a backend AND the auth question answered.

## FEED LAG, PROPERLY MEASURED + PER-MOVE ATTRIBUTION (supersedes July 31)

The July 31 cross-correlation is REPLACED. Measuring against real 1s data
(PHI@BAL, market 180) showed a reaction is not an instant — it bleeds in over
~10s — and that the lead scales with how OBVIOUS the play is:
    Home Run 17-23s early | Triple 7.7s | Double 2.8s | routine 2-4s
    median across all reactions 4.0s (our estimator says 4.0s — it agrees)
frontend/src/mlbLag.js now:
- reactions(): group consecutive moves (>=1c, gap <=4s) into bursts w/ centroid
- estimateLag() -> {lagMs = median offset of a burst CENTRE, leadMs = median
  START offset of the BIG bursts (top quartile, >=3c), samples, ...}. Needs >=5
  matched bursts (within -8s..+30s of a play stamp) or returns null.
- attributeMoves() -> every burst + the play that caused it + that burst's lead
- moveAt(attributed, ts) -> the move under the cursor
Tooltip names the cause: "price moved 68.0c — caused by Triple · 2 RBI", the
description, and "market moved 7.7s before MLB recorded it". Big attributed
moves get a ReferenceLine (green if the play scored). Readout: "≈4.0s typical ·
big moves start ~9s before the play is recorded (from N reactions)".
The -0.5s/+0.5s/auto nudges are GONE (lagOverride removed entirely).
WHY the old one said 3.5s: it anchored on play.end with a 2.5s window, so it
only ever saw the densest slice, not the leading edge.
NOTE: 5s sampling was NOT the limitation — live MLB markets poll at 1s
(verified 12,244 one-second ticks on market 180).

## MLB POLLS AT 1s, BUT ONLY WHILE THE GAME IS LIVE

Always-on 1s = 3.26M ticks/day = ~140 MB/day (measured). So:
- settings.mlb_poll_interval = 1; /events/track uses it for mlb- slugs
- scheduler.sync_mlb_intervals() every 60s: resolve each tracked MLB market's
  game, poll_interval = 1 while status==Live else default 5, then sync_jobs()
- _game_pk_cache caches ONLY successful lookups. Caching a failure would pin a
  market at 5s forever after one transient MLB error (found in code review).

## Price semantics (client asked, investigated in depth)

- Gamma `outcomePrices` == the MIDPOINT, exactly (bid+ask)/2. Verified.
  That is what the screener shows.
- Polymarket's sports "Games" view buttons show the ASK (buy price); their
  market detail "% chance" is midpoint-style.
- On liquid markets spread ~0.1c so they look identical. On illiquid ones
  (e.g. Bolivian league: bid 10c / ask 68c) mid and ask differ by 30+
  points — that was the client's reported "price mismatch". NOT a bug.
- Our tick collector stores CLOB midpoints, so keeping midpoint in the
  screener keeps screener and history consistent. RECOMMENDED (not built):
  add an illiquidity/spread flag on rows with wide bid-ask. Client has not
  chosen yet between: keep mid + flag / switch to ask.
- Also seen: Polymarket postpones fixtures (slug keeps old date,
  gameStartTime updates) — our kickoff follows gameStartTime, correct.
